## 哪些失败 / 出问题

### 1. PDF 解析失败（pymupdf）

**现象**：`cache/2404.01833.pdf` 1.3MB 但 `len(doc)==0` 且 title 是 "usenix_artifact_evaluation_available"

**根因分析**：
- arxiv PDF 端点（`https://arxiv.org/pdf/<id>`）有时返回的不是论文 PDF，而是上游服务器缓存的某个 artifact template（很可能 CDN bug 或被缓存污染）
- 进一步分析：文件大小 1.3MB 不算小，且 metadata 中 creator 是 Adobe Illustrator，但 page 数为 0——很可能是损坏的 PDF 包装
- **不是特例**：旧论文 + 某些会议 PDF + 加密 PDF + 扫描 PDF 都可能出问题

**这是 case-specific 还是底层？** **底层问题**。整个系统的论文内容获取完全依赖单一来源（PDF），而 PDF 是不可靠的。

**应该改的底层**：
- 引入 **PaperContentAdapter** 抽象层（plan §1.1）
- 当前实现采用官方源身份校验：arXiv/OpenReview/Crossref 元数据、官方 BibTeX 和正文必须分别通过脚本校验；没有通过校验的论文直接淘汰，不以未验证 fallback 填槽。
- **不要**针对某类 PDF 单独写解析补丁

### 2. 候选过滤误判（很多非 LLM 论文入选）

**现象**：862 → 146 → 20 中，有些明显不是 LLM Security（如 PowerPeeler、Auditing Unlearning）混入候选池

**根因分析**：
- 关键词 "security" / "attack" 在很多 DNN/恶意软件分类论文里也命中
- LLM 信号词（"llm" / "language model" / "gpt"）虽然要求命中，但有些标题含 "language model" 但实际主题是 NLP 任务（非安全）
- subagent reasoning 二次过滤时，误把 6 篇非 LLM 论文放进候选池（候选池 146 → subagent 选 20 时勉强凑数）

**这是 case-specific 还是底层？** **底层问题**。
- 关键词匹配 ≠ 主题匹配
- "language model" 在 2024+ 是个高度歧义词

**应该改的底层**：
- 硬过滤层加**同句检测**："security/attack/jailbreak/backdoor" 和 "llm/language model" 必须在同一句话或同一段，才算真正相关
- 软评分层加 SS citationCount（高引论文更可能是真 LLM 安全）
- 让 subagent 看的 862 候选先过 agent 自检（一句话判断是否真属于主方向），不要先按关键词粗筛再让 agent 选

### 3. arxiv 关键词检索 429 限速（仅靠 stage 1 顶会候选勉强够用）

**现象**：阶段 2 关键词检索多个 query 触发 429 限速，stage 1 顶会检索反而稳定

**根因分析**：
- arxiv API 不区分 query 类型，统一限速（每 IP ~1 req/3s）
- 我们 18 个 venue + 7 个 keyword = 25 query，间隔太短

**这是 case-specific 还是底层？** **底层问题**。
- 任何高频检索都会被限速
- 单 query 内 max_results 太小也不行（per_venue=40 时漏掉了一些新论文）

**应该改的底层**：
- 抓取层加 token bucket / 限速器（>=3s/req）
- 抓取改为"先抓 stage 1 顶会 + 等 5s + 再抓 stage 2 关键词"
- 多个官方源可并行提供候选，但不把非权威 enrichment 当作事实来源；SerpAPI Scholar 仅做精确标题后的可选 enrichment。

### 4. GitHub Pages 启用需要手动一次

**现象**：Pages 不会自动启用，需要用户在 GitHub UI 手动开启

**这是 case-specific 还是底层？** **case-specific**（仅首次需要）

**应该改的底层**：一次性手动开启就行。
